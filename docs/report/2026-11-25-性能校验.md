# 2026-11-25 性能校验

## 测试条件

- Chrome 150.0.7871.125，无界面模式，本机 Python HTTP 服务。
- 桌面视口 1440×900，每组使用全新浏览器上下文，重复 3 次，表中取中位数。
- 初始载入 → 搜索“皮卡丘”（429 条）→ 清空 → 连续点击加载更多 50 次（共 2,448 张）→ 滚动到底部 → GC 后采集堆与 DOM。
- 外部 CDN 图片统一替换成固定 1px 图片，避免网络波动影响前端性能对比；不代表真实卡图网络加载速度。
- 搜索响应包含 Playwright 操作开销、页面 160 ms 防抖和轮询观测延迟，不等同于纯筛选算法耗时。
- 首卡片就绪是首次插入卡片后的下一帧时间，不是 LCP；JS 堆不包含浏览器全部进程内存。
- 优化前取自上轮已支持 gzip 和增量追加的版本；两组在同一机器顺序执行，未对操作系统负载作严格控制。

## 手机尺寸与 CPU 降速

390×900 视口、CPU 4 倍降速，重复 3 次。这只是 CPU 模拟，不是实体手机或弱网测试。

- 首卡片就绪中位数：972.0 ms。
- 搜索响应中位数：292.3 ms。
- 加载更多中位耗时：23.0 ms。
- 2,448 张可浏览卡片只渲染 12 张，DOM 节点 2523。
- 仍观测到 344–499 ms 的首屏长任务：索引解析和对象初始化仍在主线程，较弱设备首次载入仍可能短暂阻塞。

## 校验结果

- Node 行为测试 7 项和 Python HTTP 测试 1 项通过。
- 全量 24,544 张卡牌的索引字段、招式搜索文本、详情还原、5 种排序顺序对比通过。原始 ID 存在重复，详情改按分片内位置获取。
- Chrome 桌面 1440px 和手机 390px：搜索、空结果重置、首屏不请求详情、详情展示、2,448 张列表尾部索引、窗口尺寸变化和无横向溢出均通过。
- 详情失败后重试、关闭弹窗后旧响应不重新打开弹窗均通过。
- 修复测试发现的手机关闭按钮被卡图遮挡问题。
- gzip 响应内容解压一致；客户端拒绝 gzip 时返回原文；ETag 条件请求返回 304。
- 桌面和 CPU 4 倍降速共 6 次性能运行均通过预算断言，无页面脚本异常。

## 预算与复现

性能预算为：渲染卡片 ≤80、DOM <6000、监听器 <300、首屏本地资源 <1.5 MB、加载更多中位耗时 <50 ms（CPU 模拟按倍率放宽）。详见根目录 README 的复现命令。

## 已知边界

- 外部图片带宽、真实网络下的 LCP/CLS、真实手机电量和多浏览器兼容性未作本轮性能结论。
- 详情由点击时的网络请求取得；请求失败时可重试，最多缓存 8 个分片。列表图片失败时展示简要文字卡面，详情页展示完整文字卡面。
- 虚拟列表用固定元数据高度计算行高，长卡名在列表截断，详情页可查看完整名称；新增卡片样式需同步验证虚拟列表行高。
- 原始数据更新后必须重新构建索引与详情并一起部署；旧详情版本不能在仍有旧页面访问时立即清理。
