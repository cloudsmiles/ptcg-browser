# 2026-11-25 缩略图与首屏索引优化

列表改为同源 WebP 缩略图：240/480 两档由浏览器按像素密度选择。原图不足 480 像素时保持原尺寸，不放大。详情仍访问原始图片。

## 真实卡图抽测

本机真实网络获取，不拦截、不替换图片；依次请求原图、缩略图首次请求、缩略图磁盘缓存请求。480 档、WebP quality=80。样本不是随机抽样，不代表所有卡牌。

| 样本 | 原图合计 bytes | WebP 合计 bytes | 体积减少 | 缓存响应中位数 ms |
|---|---:|---:|---:|---:|
| 能量卡（8 张） | 1,452,345 | 151,222 | 89.6% | 2.5 |
| 宝可梦卡（8 张） | 2,202,501 | 240,902 | 89.1% | 2.2 |

冷缓存能量卡首次生成约 358–617 ms，明显慢于本次多数直接 CDN 请求。原因是服务需再次下载原图并生成两档缩略图；本轮已预热默认列表前 48 张。宝可梦样本在预热之后测量，其“首次缩略图请求”已命中磁盘缓存，不能当作冷缓存数据。缓存响应的本机耗时也不能外推为远端部署延迟。

缩略图 URL 含仓库提交版本，响应 `Cache-Control: public, max-age=31536000, immutable`，浏览器可长期缓存。服务一次生成两档，共用原图下载；最多 4 个并发源图下载，固定来源与路径校验、单文件大小/像素限制均已加入。

## 索引解析

重复字符串用字典编号引用，索引未压缩体积 10,089,343 → 8,075,523 bytes，减少约 20%；gzip 约 1.33 MB → 1.29 MB。对比双方使用相同的新加载器，分别用 5 个独立 Node 进程运行：编译、执行、对象还原总耗时中位数约 158.5 → 155.6 ms。差异很小，不能宣称明显提速；真实浏览器首屏仍受主线程解析影响。

固定图片的 Chrome 3 次测试通过现有性能预算，无脚本异常，加载更多中位数约 14.7 ms。该测试仅用于前端回归，不用于评价真实图片加载速度。真实卡图另用未拦截图片的浏览器脚本检查 DPR 1/2 首屏实际图片可解码显示。

## 测试与复现

- Node 7 项行为回归，Python 3 项测试（HTTP 协商与缩略图尺寸/缓存/失败恢复）。
- 真实 Chrome 验证：DPR 1/2 选择正确档位、详情使用原图、缩略图失败移除 srcset 后回退原图。
- 无文字占位、桌面和手机滚动稳定性、搜索、详情、尾部定位、窗口尺寸变化和详情失败重试回归。
- 按用户要求不使用预热，预热脚本已移除；上述涉及预热的记录仅说明此前测试条件。
- 公网样本：`node scripts/thumbnail-benchmark.cjs`。
- 实际卡图浏览器：`node scripts/browser-real-thumbnails.cjs`（需设置 README 中的 `PLAYWRIGHT_CORE`）。

## 部署与边界

新增 Pillow 依赖，见 requirements.txt。服务仍用 `python3 serve.py` 启动。`.cache/thumbnails` 是可重建磁盘缓存，未实现磁盘总量自动淘汰，需按旧版本清理。静态托管必须提前生成缩略图文件或代理缩略图服务；不提供此路径时浏览器回退原图。

运行时仅按需生成，不主动提前下载卡图；未缓存卡片可能遇到冷缓存延迟。缩略图服务依赖部署机器能访问固定原图库，并未修改第三方 CDN 本身。
