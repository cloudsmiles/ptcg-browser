# 服务器部署与自动同步

## 部署布局

- 代码仓库：`https://github.com/cloudsmiles/ptcg-browser.git`。
- 网站入口：`http://159.75.178.17/ptcg/`。
- 代码版本目录：`/www/ptcg-browser/releases/<提交标识>`，`current` 链接指向当前版本。
- Python 依赖：`/www/ptcg-browser/venv`；要求 Python 3.11+、Node.js 22+。
- 数据与同步状态：`/var/lib/ptcg-browser`。
- 缩略图缓存：`/var/cache/ptcg-browser/thumbnails`。
- 网页服务：`ptcg-browser.service`，只监听 `127.0.0.1:8096`，由现有 Nginx 代理 `/ptcg/`。
- 数据任务：`ptcg-data-sync.service`；定时器为 `ptcg-data-sync.timer`。

服务使用独立系统用户 `ptcg`。数据任务只可写数据目录，网页服务只可写缓存目录；网页不提供代码、Git 元数据或目录列表。登录凭据不属于项目配置，不得提交到 Git。

## 首次安装

以管理员身份创建独立用户和上述目录；代码及虚拟环境归管理员所有，数据与缓存目录归 `ptcg` 所有。将测试通过的 Git 提交解包到新的代码版本目录，再创建 `current` 链接。在虚拟环境执行 `python -m pip install -r requirements.txt`。

将 `deploy/ptcg-*.service` 和 `deploy/ptcg-data-sync.timer` 安装至 `/etc/systemd/system/`。使用 `systemctl daemon-reload` 载入配置后，先运行一次 `systemctl start ptcg-data-sync.service`，确认同步成功，再执行：

```sh
systemctl enable --now ptcg-browser.service
systemctl enable --now ptcg-data-sync.timer
```

本服务器的现有站点会加载 `/www/server/panel/vhost/nginx/extension/159.75.178.17/*.conf`，将 `deploy/ptcg-nginx.conf` 放入该目录。用 `/www/server/nginx/sbin/nginx -t` 检查成功后再执行 `/www/server/nginx/sbin/nginx -s reload`。保留原站点和其他服务的配置。

## 日常检查

每天北京时间 04:15 开始检查，增加最多 5 分钟随机延迟；服务器关机错过的任务在恢复后补执行。没有数据变化时不会重新下载和构建。

```sh
systemctl list-timers ptcg-data-sync.timer --all
systemctl status ptcg-browser.service ptcg-data-sync.timer
journalctl -u ptcg-data-sync.service -n 80 --no-pager
cat /var/lib/ptcg-browser/status.json
```

手动检查或立即同步：

```sh
cd /www/ptcg-browser/current
runuser -u ptcg -- /www/ptcg-browser/venv/bin/python sync_data.py --state-dir /var/lib/ptcg-browser --check
systemctl start ptcg-data-sync.service
```

同步失败时旧版继续服务，查看日志定位网络、上游格式或数量异常。GitHub 公共 API 有匿名调用频率限制；如频繁手动检查而触发限额，可在服务器独立的受保护环境配置中提供 `GITHUB_TOKEN`，不要写入代码或日志。上游未收录的卡牌不会由本项目自行补齐。

## 代码更新

代码提交与推送后，将该提交打包上传到新的版本目录。安装依赖并以新代码完成同步检查、测试后，原子切换 `current` 链接，重启 `ptcg-browser.service`。数据和缓存独立于代码目录，不会因代码切换丢失。若更新了 systemd 或 Nginx 配置，重新安装相应文件并检查后载入。

GitHub Actions 仅验证代码，不接收服务器登录凭据，也不自动部署推送的代码。线上数据同步不依赖 Git 仓库的定时提交。

## 回退

代码回退：将 `current` 链接切回之前的提交目录，然后重启网页服务。不要删除旧版本数据资源。

数据回退：先停止 `ptcg-data-sync.timer`，确认数据任务未运行；状态目录中 `previous-bootstrap.js` 和 `previous-status.json` 保存上次发布前的入口及状态。使用同目录临时文件加原子替换，将它们分别恢复为 `data/zh-bootstrap.js` 和 `status.json`。网页服务无需重启。先确认备份确实是需要的版本；首次发布不存在备份。处理完上游问题后再启动定时器，否则保持暂停以免下一次同步又发布相同问题版本。

## 空间维护

当前保留历史索引、详情和缩略图，暂无自动空间上限。定期检查数据和缓存磁盘占用；清理旧资源前确认没有需要保留的旧页面和回退版本。缩略图缓存可按上游提交目录删除，后续访问会重新生成；勿在数据任务运行时清理数据目录。

### 卡图压缩与后台生成

列表仅请求 `/thumbnails/v2/<版本>/240|480/<系列>/<编号>.webp`，没有原图降级；失败时显示提示，暂未生成则自动重试缩略图。详情点击后请求同一路径下的 960 档压缩 WebP，不向浏览器发送 PNG 原图。所有尺寸都保持比例且不放大。

列表使用 WebP quality=45，详情 quality=60，均使用 method=6 压缩；生成文件放在缓存的 `v2/` 子目录，避免复用旧压缩参数的文件。新路径也避开浏览器已保存一年的旧缩略图。原始 PNG 只在服务器缓存中用于生成，避免反复下载上游。

缓存未生成时接口立即返回不缓存的 HTTP 202、`Retry-After: 2` 和 320×1 透明 SVG 标记；列表显示“图片加载中”，详情保留文字卡面，前端每隔 1.5～2.5 秒重试当前缩略图，最多 30 次。重试耗尽时列表显示“图片暂不可用”。同一卡的 240、480、960 档共用一个后台生成任务与原图缓存。

后台使用 8 个工作线程，最多保留 128 个排队任务；队列满时前端下次重试再提交。下载按 GitHub Raw、jsDelivr Gcore、jsDelivr 顺序回退，共用 16 秒预算，单次网络等待最多 4 秒。校验和生成成功后原子写入缓存；失败任务释放，后续可重试，失败详情记入日志。上游持续不可达时仍无法展示卡图。
